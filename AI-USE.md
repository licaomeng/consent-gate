# AI Use

I used OpenAI Codex to analyze the brief, compare this starter with an earlier practice implementation, challenge design assumptions, and edit the documentation. I chose the product semantics, reviewed the diffs and verification output, rejected unsupported claims, and remain responsible for the submission.

Implementation milestones M1–M4 were produced with Claude Code as the primary agent, with a separate read-only adversarial reviewer sub-agent for each milestone.

## TL;DR

- **Tools:** OpenAI Codex for brief analysis, design challenge, and documentation review; Claude Code for implementation, tests, and one read-only adversarial reviewer sub-agent per milestone.
- **Errors caught and fixed:** a design claim that E2E gated deployment while CI ran only coverage and build; reused requests documented as always `pending`; fixed-date demo presets that drifted from the engine; cross-bundle `instanceof` turning 409/400 into 500 in production; two live regions announcing the same status twice.
- **Discarded:** editable subject identity, colour-only status, client-side policy evaluation, and removing the globalThis container singleton (it would reintroduce HMR state loss).
- **Evidence:** the per-milestone log below; 172 Vitest tests, 19 Playwright journeys, 8/8 HTTP smoke, and 23 mutation checks across M1–M3.

## Material contributions

- Converted open requirements into explicit policy, consent, API, UI, and test contracts.
- Compared the proposed design with an earlier implementation and retained useful demo and testing ideas without copying its client-side policy logic or production claims.
- Checked consistency across the design, deployment workflow, and reviewer-facing documents.
- Established the implementation working method recorded in `AGENTS.md`: a primary agent owns contracts and integration; independent read-only agents cover orthogonal review angles; each milestone ends with focused tests, an adversarial reviewer using a different angle from the previous round, a failing test for each accepted defect, and a mutation check for each new safety rule. Results are recorded in the review log below.

### M1 review corrections

Initial M1 implementation: [`4c504ec`](https://github.com/licaomeng/consent-gate/commit/4c504ec). Review hardening: [`9d137a1`](https://github.com/licaomeng/consent-gate/commit/9d137a1). All four findings below came from the **user's own review**, not from the agent's first-pass reviewer.

1. **[User review] Jurisdiction normalization depended on the caller.** `evaluateDecision` / `resolveRule` matched the raw string, so a caller that skipped `parseScenario` could pass `gb`; it fell through to the `*` consent rule while the `GB` hard block sat unused. Fix: `resolveRule` now normalizes and validates at its own boundary. Tests: raw `gb` + an approved consent → `blocked / under_minimum_age`; `g!` → `validation_error`.
2. **[User review] The shared policy was mutable and `matchedRule` leaked the internal rule object.** `readonly` is compile-time only; once the policy becomes a module singleton, a downstream mutation of a result could change later decisions. Fix: freeze the policy, the rule array, and every rule, and return a copy of `matchedRule`. Tests: mutating a frozen rule throws; mutating a result leaves the policy unchanged.
3. **[User review] Implausible birth dates satisfied every age threshold.** `0000-01-01` and `1800-01-01` were accepted. Fix: reject calendar dates before 1900 and record that choice in `DECISIONS.md`. Tests: `0000-01-01`, `1800-01-01`, and `1899-12-31` are rejected both directly and through `parseScenario`.
4. **[User review] `AI-USE.md` said the implementation tool would be recorded later.** Fix: name Claude Code as the implementation tool, add this review log, and state the verification results.

### M2 review corrections

Initial M2 implementation: [`16f130d`](https://github.com/licaomeng/consent-gate/commit/16f130d). Review fixes: [`ccbc854`](https://github.com/licaomeng/consent-gate/commit/ccbc854).

1. **[Agent reviewer] Configuration failures were lazy and reported as client errors.** The container loaded the policy and read the evaluation date on the first request, so an invalid `policy.json` or `CONSENT_GATE_EVALUATION_DATE` produced `400 validation_error` — a client-blaming answer for a server misconfiguration. Fix: the container is created eagerly at module load (build/startup) and validates the clock at construction. Test: `createContainer()` throws when the evaluation date is invalid.
2. **[Agent reviewer] `created` was inferred from the pre-write lookup.** A conforming production repository can deduplicate inside `create` (unique constraint), so answering `201 created:true` from the earlier lookup could lie. Fix: `create` returns `{ request, created }`; the service reports `created` from the write result. Test: a repository whose lookup misses but whose write deduplicates returns `created:false`.
3. **[Agent reviewer + mutation check] Test gaps closed.** Route-level `503` for all four operations, read-only `POST /decisions` proven over HTTP, subject isolation over HTTP, `409` for adults and coverage gaps, error-message presence, and the policy-drift case where an existing record must be returned before re-evaluating eligibility under a new hard-block policy.
4. **[User review] A blank test-clock override crashed startup, and production could freeze every age.** `?.trim()` returned `""`, which `??` treated as set, so `CONSENT_GATE_EVALUATION_DATE=""` reached `parseCalendarDate` and failed during eager container creation. Separately, an accidental production value would freeze the evaluation date. Fix: blank means unset, and the override is honored only with the explicit `CONSENT_GATE_ALLOW_TEST_CLOCK=1` opt-in. Tests cover blank, absent flag, present flag, invalid value, and the in-process pin taking precedence.
5. **[User review] 503 and 500 responses were unlogged.** The routes caught every error, so operators saw no stack trace. Fix: `console.error` before returning 503 or 500; expected 4xx errors are not logged and response bodies are unchanged. Tests assert one log for each server error and none for domain errors.
6. **[User review] The container was a module-local singleton.** A Next.js module reload could reset the in-memory consent store mid-demo. Fix: store the container on `globalThis`, the standard shared-singleton pattern. Test: repeated reads return the same instance and replacement/reset still work.
7. **[User review, rejected] A row vanishing between `getById` and `updateStatus` should return 404 instead of 503.** Rejected: the in-memory repository never deletes, there is no `await` between the check and the write, and `DECISIONS.md` explicitly places cross-process concurrency outside the exercise's guarantees. The boundary is documented on the repository interface: the pre-write `getById` owns the 404; a write failure is a storage inconsistency (503).

### M3 review corrections

All seven findings below came from the **agent's adversarial reviewer**.

1. **"Ask a parent" could reappear for a pending request.** `actionsFor` keyed only on `decision === "parental_consent"`, so a decision with reason `parental_consent_pending` and no locally-found request exposed the explicit write again. Fix: require `reason === "parental_consent_required"`; tests cover the pending reason.
2. **Client scope matching ignored jurisdiction normalization.** The raw draft (`de`, ` DE `) was compared with the server-normalized request (`DE`), so an existing pending request was missed. Fix: use `decision.lookupPath[0]` (the server-normalized jurisdiction) for the scope match instead of duplicating the normalization rule. E2E: type `de` after creating a request and still see it.
3. **A failed consent-state read was converted to "no request".** A non-2xx `GET /consent-requests` returned `null`, which re-exposed Ask. Fix: throw and abort the check with an alert; never manufacture "no request". E2E intercepts the GET with 503.
4. **Preset expected outcome and purpose were never shown.** DESIGN §4 requires them before evaluation. Fix: presets carry a `purpose`, and selecting one renders `expected` + `purpose`; the contract test keeps the expectation aligned with the engine.
5. **No "Waiting for parent" state.** Fix: render it when the decision reason is `parental_consent_pending`; asserted in the consent-loop journey.
6. **A failed post-action refresh kept stale evidence.** If PATCH succeeded and the fresh decision failed, the old decision sat beside the new request status. Fix: clear the decision and show a retryable error; the confirmed request stays visible per DESIGN §5. E2E fails the second decision call.
7. **Progress and request status were not announced.** Fix: a `role="status"` live region for the phase and `aria-live` on the parent status. E2E asserts "Checking access…" while a delayed check is in flight. The parent-status live region was later replaced by the single decision-summary region to avoid a duplicate announcement (see M5 follow-up review corrections).

### M3 second review corrections

Initial M3 implementation: [`dfe27ed`](https://github.com/licaomeng/consent-gate/commit/dfe27ed). Second-review fixes: [`d8bc9be`](https://github.com/licaomeng/consent-gate/commit/d8bc9be). All four findings below came from the **user's review**.

1. **[User review] Preset expectations were tied to a fixed date.** DOBs were hardcoded and the contract test pinned `2026-10-19`, while the server uses its current date; from 2027 the California preset, and later others, would show an expectation the engine no longer returned. Fix: presets carry an age, and the DOB is derived from the server's evaluation date (the page is dynamic and receives that date). The contract test now runs every preset on four dates through 2040.
2. **[User review] E2E could silently reuse an unrelated server.** `reuseExistingServer: true` on port 3000 meant a local dev server would be reused without the pinned clock environment. Fix: a dedicated port (3100), `reuseExistingServer: false`, and the consent-loop journey asserts `evaluatedAt` is the pinned date.
3. **[User review] `AI-USE.md` contradicted itself.** The verification block still said "no product tests yet" and "verify not yet run" beside "10 journeys passing". Fix: the stale lines were removed and the actual `npm run verify` result is recorded; empty-suite allowances were removed in M4.
4. **[User review] Scenario inputs stayed editable during an in-flight write.** Editing during `creating_request` or `updating_request` invalidated the token and dropped a response after the server may have committed it. Fix: the three inputs are disabled while busy and `updateDraft` refuses changes during a write. A Playwright journey locks the jurisdiction input during a delayed PATCH. Because operations are now serialized, the request-token guard is defence in depth rather than a reachable path; its pure function remains unit-tested.

### M4 review corrections

Initial M4: [`a409eab`](https://github.com/licaomeng/consent-gate/commit/a409eab). Review fixes: [`d013796`](https://github.com/licaomeng/consent-gate/commit/d013796). All findings below came from the **agent's documentation-vs-artifact reviewer** and the **user's review**.

1. **[Agent reviewer] The final sentence contradicted the verification block.** "Before submission, I will record… Empty-suite allowances will be removed" was stale beside the recorded verify result. Fix: replaced with an explicit pending-deployment statement; the allowances are already removed.
2. **[Agent reviewer] README called the API "four routes".** There are three route files implementing four operations. Fix: the wording now distinguishes route files from operations.
3. **[Agent reviewer] The smoke and mutation claims had no repository artifact.** They lived only in a temporary directory. Fix: landed `tools/http-smoke.sh` and `tools/mutation-check-m{1,2,3}.sh`, made them path-relative, and re-ran the HTTP smoke and the M1 mutations from the repository.
4. **[Agent reviewer] Several documents under-claimed or retained stale framing.** The M3 allowance note, the M1-only tool attribution, the DESIGN/DECISIONS "proposed/target" framing, and the "path CI uses" wording were corrected to match the delivered state.
5. **[User review] The mutation scripts could leave broken code after an interrupt.** They edited real source files with no trap; a Ctrl-C during the M3 build/Playwright window would leave the mutated safety rule in `src/`, and the next `git add -A` boundary could commit it. Fix: each script snapshots `src/`, installs `trap cleanup EXIT INT TERM`, and uses a per-run `mktemp -d` for backups and logs.
6. **[User review] The production error regression was guarded only by a manual smoke.** CI runs coverage, build, and E2E, and the unit tests use plain objects that cannot reproduce the bundle split. Fix: three Playwright API journeys now assert `409 consent_not_required`, `400 validation_error`, and `404 request_not_found` against `next start`, so `verify` and CI cover the error contract.
7. **[User review] The smoke could pass against a foreign server.** If port 3200 was busy, the new process died and curl could talk to an old one. Fix: fail when the port is in use, verify the started process is still alive after readiness, and fail on `EADDRINUSE`.
8. **[User review, rejected] Moving the container off `globalThis` would remove the cross-bundle condition.** Rejected: removing the singleton would reintroduce the development-time state-loss issue fixed in M2. Structural error classification is the correct boundary; the reasoning is recorded in `docs/DESIGN.md`.
9. **[M4 HTTP smoke] The production build turned expected 4xx errors into 500.** The smoke returned 500 for a hard-block create (expected 409) and a client-supplied evaluation date (expected 400), with the log showing the errors were `DomainError`s. Cause: the route handler and the services are bundled separately, so `instanceof DomainError` was false across two copies of the class. Fix: classify errors structurally by the stable `name` plus the closed set of domain codes; the client-facing contract is unchanged. Tests: foreign-shaped domain/repository errors are recognised, while a primitive, `null`, or an unknown code stays a 500. The rebuilt HTTP smoke is 8/8.

### M5 front-end review corrections

All findings came from the user's front-end review, checked against the earlier practice repository.

1. **The nature of each demo was hidden until after selection.** The cards now show a visible expected tag (`Allowed`, `Blocked`, `Needs consent`) and a one-line purpose before the user clicks, and the selected card exposes `aria-pressed`.
2. **There was no semantic colour.** Decision cards now use green/amber/red, request status is a coloured badge (pending/approved/declined), and Approve/Decline are green/red. Every colour is paired with text.
3. **Raw codes were shown as the primary copy.** Features, reasons, and statuses now have human-readable labels; the stable reason code remains visible in a `<code>` element.
4. **There was no expected-vs-actual comparison.** Selecting a preset and evaluating now shows `Expected … · Actual …` in the decision card; the preset contract test remains the source of truth.
5. **The flow and empty state were unexplained.** The page now uses numbered steps 0–3, the demo section explains fresh subjects, the parent empty state gives the next action, and the policy panel explains precedence and its source.
6. **Accessibility was incomplete.** Added programmatic labels, `aria-pressed` on demo cards, `aria-live` + `aria-atomic` on the decision region, `role="status"` for progress, `aria-busy` on the child panel, `role="alert"` for errors, a table caption and column headers, visible focus rings, and native disabled states while a request is in flight. (The parent-status live region added here was later removed to avoid a duplicate announcement; see M5 staged-diff review corrections.)
7. **The synthetic subject id was opaque.** It is now prefixed with the preset id (for example `german-child-chat-…`) while remaining fresh per selection.

### M5 follow-up review corrections

1. **Help icons sat far from the control they explain.** The heading row let the longer description paragraph determine the text block's width, so the icon landed after that width instead of beside the heading. The icon now sits in a `.heading-line` next to the title, and **New subject** keeps its icon in the same `.subject-actions` group as the button.
2. **The subject id was truncated to 32 bits.** `newSubjectId` now stores a full UUID (or a 128-bit `getRandomValues` fallback) and `displaySubjectId` shortens only what the page renders. Measured before: `crypto.randomUUID().slice(0, 8)`; the reviewer's collision claim was overstated, but enumeration of a 2³² capability is the real axis and the fallback used `Math.random`. The first version of the display matcher dropped the UUID separator; the new E2E assertion caught it (`manual-12ad4678-1e95-…` was rendered in full) and the matcher was fixed before the final run.
3. **Three live regions could announce the same status.** Runtime `MutationObserver` on the pending→approved transition showed, before the fix, `request-status` and `decision-summary` updating in the same tick (12 ms), with the summary briefly reading "Needs parental consent … Status: Approved" before settling at 18 ms. Fixed by removing `role`/`aria-live` from the visible status badge and committing the request status and fresh decision in one render. Re-measured after the fix: one summary mutation with the settled text (`Allowed … Status: Approved`), `request-status` with `role=null` and `aria-live=null`. The E2E now asserts the single summary carries `Status: Pending`/`Status: Approved` and that the badge is not a live region.
4. **Tooltips did not meet WCAG 1.4.13 dismissal.** Measured before: pressing Escape left the tooltip at `opacity: 1`; visibility came only from CSS `:hover`/`:focus-within`. Fixed with state-driven visibility: click toggles, Escape and outside presses close, and hover/focus still work. Re-measured: Escape while focused or hovering fades the tooltip to 0; a click without hover opens it (`data-open="true"`). The touch claim was not verified on a device; click toggling makes it deterministic. Playwright now asserts Escape hides the tooltip and a click without hover opens and closes it.
5. **`next-env.d.ts` was staged with dev paths.** The staged diff changed `.next/types` to `.next/dev/types`. The claimed clean-checkout `tsc` failure did not reproduce (a temp project with no `.next` exited 0), and CI only runs `build`/`test:e2e`, so this was generated churn. The file is now untracked and listed in `.gitignore`, so `next dev` and `next build` stop dirtying the tree.
6. **Timestamps used the viewer's locale.** `toLocaleString()` rendered an unlabelled local time beside a date-only `evaluatedAt`. They now render as UTC strings inside `<time dateTime>` elements. No existing test read those strings, so the reviewer's "tests depend on the runner's locale" claim was corrected; the E2E now asserts the UTC label.
